# CP-007: 이메일 로그인 유지 및 아이디 로그인 추가 실행계획

- 작성일: 2026-08-31
- 상태: 실행계획 작성 완료 / 정책·DB·API 변경 승인 전
- 요청: 기존 이메일 + 비밀번호 로그인에 아이디 + 비밀번호 로그인 추가
- 이번 산출물: 실행계획만 작성. 애플리케이션 코드, 잠금 문서, DB는 변경하지 않음.

## 1. 목표와 권장 정책

같은 계정에 이메일과 로그인용 아이디를 연결하고, 동일한 비밀번호로 로그인한다. 두 입력 방식 모두 기존 User.id를 사용하므로 콘텐츠·결제·권한·세션의 계정 기준은 바뀌지 않는다.

다음 정책은 사용자 확정 사항이 아닌 구현 기본안이다.

| 항목 | 제안 |
|---|---|
| 로그인 폼 | `아이디 또는 이메일` 입력 한 칸 + 비밀번호. 별도 탭 없음 |
| 신규 회원가입 | 이메일·비밀번호 필수 유지, 아이디는 선택 입력 |
| 기존 회원 | 이메일 로그인 유지. 프로필 설정에서 아이디를 직접 등록 |
| 아이디 형식 | 영문자로 시작하는 영문·숫자·밑줄 4~20자. 앞뒤 공백 제거 후 소문자로 저장·조회 |
| 아이디 중복 | 대소문자를 구분하지 않음. 서버 검증과 DB unique 제약으로 보장 |
| 아이디와 이메일 구분 | 아이디에 `@` 금지. 입력에 `@`가 있으면 이메일 경로, 없으면 아이디 경로 |
| 아이디 변경 | 1차에서는 최초 등록만 허용. 등록 후 조회 가능, 변경·삭제·재사용은 제외 |
| 아이디 등록 보호 | 로그인한 비밀번호 보유 회원만 현재 비밀번호 확인 후 등록 |
| 소셜 계정 | 기존 소셜 로그인 유지. 비밀번호가 없는 계정의 아이디 로그인·최초 비밀번호 설정은 이번 범위에서 제외 |
| 계정 복구 | 기존 이메일 기반 비밀번호 재설정 유지. 아이디를 잊으면 이메일로 로그인해 프로필에서 확인 |

이메일 앞부분이나 표시 이름을 아이디로 자동 지정하지 않는다. 이메일의 기존 대소문자 저장·조회 정책도 이번 변경에서 일괄 변경하지 않는다. 비밀번호는 공백 제거·소문자 변환 없이 원문으로 검증한다.

## 2. 현재 구현 확인

| 영역 | 현재 상태 | 필요한 변경 |
|---|---|---|
| `app/lib/auth.ts` | Credentials가 email/password를 받아 email로 findUnique 조회 | identifier 기반 이메일/아이디 분기, 기존 email 요청 호환 |
| `app/prisma/schema.prisma` | User에 email/name/passwordHash가 있고 username은 없음 | nullable unique username 추가 |
| `app/app/(public)/login/login-form.tsx` | type=email 입력, 이메일 전용 문구 | type=text, 통합 레이블·검증·자동완성 |
| `app/app/(public)/register/page.tsx` | 이메일·비밀번호 가입 후 이메일로 자동 로그인 | 선택 아이디 입력, 중복 안내, 자동 로그인 회귀 확인 |
| `app/app/api/auth/register/route.ts` | email/password 검증 및 생성 | username 검증·저장, unique 충돌 처리 |
| `app/app/(app)/settings/profile/page.tsx` | 이름·이메일 표시, 이름/비밀번호 변경 | 아이디 조회·최초 등록 및 현재 비밀번호 확인 폼 |
| `app/app/api/user/me/route.ts` | GET 프로필, PATCH 이름 또는 비밀번호 변경 | username 조회 및 최초 등록 계약 추가 |
| `app/tests/e2e/pages/auth-pages.spec.ts` | 페이지·폼 노출 위주의 테스트 | 실제 로그인·등록·기존 계정 회귀 시나리오 보강 |

현재 register 및 user/me 응답은 문서의 `{ success, data/error, code }` 규약과 다르며, PATCH user/me는 계약 문서에 없다. 변경 시 소비 코드도 함께 맞춰야 한다. user/me GET의 소비자로 카드뉴스 편집 화면(`app/app/(app)/carousel-lab/page.tsx`)이 확인되었다.

테스트 설정은 `app/tests/e2e/playwright.config.ts`에 있지만 testDir는 `./tests/e2e`, baseURL은 3002이고 일부 테스트 URL은 3000으로 고정되어 있다. 테스트 탐색 경로와 실행 포트를 먼저 맞춰야 한다.

## 3. 실행 순서

### 단계 1 — 계약·화면 명세 확정

1. 위 정책과 이 제안서 승인 후에만 DB 스키마 및 잠금 문서를 수정한다.
2. `docs/db-schema.md`에 User.username을 추가하고, `docs/api-contract.md`에 아래 변경 계약을 기록한다. 다른 기존 문서 불일치를 통째로 재작성하지 않는다.
3. 로그인·회원가입·프로필의 입력 위치, 오류·로딩·등록 완료 상태를 명세하고 `docs/ux-copy.md`와 맞춘다.
4. 기존 shadcn/ui, Tailwind, CSS 변수 토큰으로 변경 부분을 구현한다. 전체 화면 재디자인이나 전역 테마 변경은 하지 않는다.

### 단계 2 — 행동 시나리오 및 테스트 선행

1. `docs/bdd/Epic1-auth.md`에 아래 완료 기준을 Given/When/Then으로 추가한다.
2. Playwright 설정의 testDir·config 지정·baseURL 및 하드코딩 URL을 정리한다.
3. 격리된 테스트 DB에 비밀번호 보유 회원, 아이디 없는 기존 회원, 소셜 전용 회원, 차단 회원을 준비한다. 운영 계정은 사용하지 않는다.
4. 로그인과 등록 실패 시나리오를 먼저 작성해 신규 기능의 실패를 확인한다. OAuth·메일 발송은 모의 처리하되 Credentials·DB 핵심 경로는 실제 검증한다.

### 단계 3 — DB 확장

1. User에 `username String? @unique`를 추가한다. User.id/name/email은 그대로 유지한다.
2. 소문자 정규형·허용 형식을 보장하는 DB CHECK와 unique 제약을 마이그레이션에 포함해 직접 쓰기나 동시 요청에서도 정합성을 유지한다.
3. 기존 회원은 username=null로 유지한다. 강제 백필이나 임의 아이디 발급은 없다.
4. 현재 DB와 마이그레이션 이력의 불일치를 점검하고, 이 기능의 컬럼·제약만 추가하는 SQL인지 검토한다. 운영 DB에 reset 또는 무검토 db push를 실행하지 않는다.
5. 테스트 DB에서 마이그레이션과 Prisma Client 생성을 검증한다.

### 단계 4 — 인증 및 저장 로직

1. 공통 Zod 스키마를 `app/lib/validations/`의 계약된 구조에 두고 아이디 정규화·형식 검증을 가입/설정/로그인에서 공유한다. 새 패키지는 추가하지 않는다.
2. Credentials의 주 입력을 identifier/password로 바꾼다. 기존 email/password 요청은 호환 입력으로 유지한다. identifier가 명시되어 잘못된 경우 email로 재시도하지 않고 거부한다.
3. 검증한 identifier를 이메일 또는 username으로 정확히 조회한다. 이메일 앞부분·name·내부 User.id로 추측 조회하지 않는다.
4. 기존 bcrypt 비교, isBlocked 검사, passwordHash 없는 계정 거부, role·JWT·세션 콜백을 유지한다.
5. 로그인 실패 문구는 `아이디 또는 이메일과 비밀번호를 확인해주세요.`로 통일해 계정 존재 여부나 차단 여부를 공개하지 않는다. 입력 누락·형식 오류는 별도로 안내한다.
6. 회원가입은 선택 username을 저장한다. 사전 중복 조회만 믿지 않고 DB unique 충돌도 처리한다.
7. 프로필 아이디 등록은 세션의 user.id만 대상으로 한다. 현재 비밀번호와 계정 상태를 확인하고 `username IS NULL` 조건으로 원자적 갱신하여 중복 클릭·동시 최초 등록을 처리한다.
8. 기존 이름 변경·비밀번호 변경·아이디 등록 요청을 명확히 구분한다. 여러 작업을 섞은 PATCH 요청은 검증 오류로 거부한다.

### 단계 5 — 화면 연결

1. 로그인: 통합 입력에 type=text, autoComplete=username, autoCapitalize=none, spellCheck=false 적용. 비밀번호는 autoComplete=current-password 적용. 레이블과 입력을 연결한다.
2. 회원가입: 선택 아이디 필드 및 형식 안내 추가. 빈 선택 입력은 null로 저장하고 저장 시 중복 오류를 표시한다. 별도 공개 중복조회 API는 만들지 않는다.
3. 프로필: 미등록 회원에게 현재 비밀번호 확인을 포함한 등록 폼을 표시하고, 등록된 아이디는 읽기 전용으로 표시한다. 비밀번호 없는 회원에게는 소셜 로그인 안내를 표시한다.
4. 프로필 데이터는 서버에서 필요한 값만 읽어 클라이언트 폼에 전달한다. passwordHash는 전달하지 않고 hasPassword 같은 최소 상태만 사용한다. useEffect 직접 fetch와 새 상태관리 의존성은 추가하지 않는다.
5. 기존 회원가입 자동 로그인과 로그인 후 원래 목적지 복귀를 확인한다. API 응답 변경에 영향을 받는 프로필·카드뉴스 등 소비 코드를 함께 수정한다.

### 단계 6 — 검증·배포

1. 아래 완료 기준의 Playwright/통합 테스트, `npx tsc --noEmit`, `npm run build`를 실행한다.
2. 로그인 시도 제한이 배포 계층에 있는지 확인한다. 현재 검색한 애플리케이션 코드에서는 limiter가 확인되지 않았다. 기존 방어가 있다면 아이디/이메일 경로 모두 적용되는지 확인하고, 없다면 별도 보안 변경안과 함께 배포 전 처리 여부를 명시한다. 프로세스 메모리 제한만으로 운영 방어가 완료됐다고 간주하지 않는다.
3. 배포 전 DB 백업·마이그레이션 상태를 확인한다. nullable 컬럼·제약 추가 → 서버의 구/신 요청 호환 → 새 화면 공개 순서로 적용한다.
4. 운영 확인은 이메일 로그인·아이디 로그인·소셜 로그인 및 기존 계정 데이터 보존을 대상으로 한다. 로그인 실패율·가입 중복 오류·서버 오류를 관찰하되 비밀번호·토큰·전체 요청 본문을 로그에 남기지 않는다.
5. 문제 발생 시 앱을 이전 버전으로 되돌리고 username 컬럼·등록 데이터는 유지한다. 이메일 로그인으로 복구 가능하며, 롤백 때문에 아이디 데이터를 삭제하지 않는다.
6. 구현·검증 결과는 `logs/`에 기록한다. 현재 workflow_state의 오래된 Sprint 상태를 임의로 완료 처리하지 않는다.

## 4. API 변경 계약 초안

Auth.js 핸들러 응답은 Auth.js 규약을 유지하며 일반 API 응답 포맷으로 감싸지 않는다.

| 대상 | 변경 요청 | 성공 응답 핵심 | 오류 |
|---|---|---|---|
| Credentials | `{ identifier, password }`; 기존 `{ email, password }` 호환 | 기존 Auth.js 로그인 결과·동일한 세션 사용자 | 인증 실패 시 통일된 로그인 오류 |
| POST /api/auth/register | `{ email, password, username? }` | 201, `{ success: true, data: { user: { id, email, username } } }` | 422 VALIDATION_ERROR, 409 USERNAME_TAKEN 또는 EMAIL_TAKEN, 500 INTERNAL_ERROR |
| GET /api/user/me | 기존 세션 인증 | 200, `{ success: true, data: { user: { 기존 공개 필드, username, hasPassword } } }` | 401 UNAUTHORIZED, 404 NOT_FOUND, 500 INTERNAL_ERROR |
| PATCH /api/user/me | 아이디 등록 `{ username, currentPassword }`; 기존 이름/비밀번호 변경 유지 | 200, `{ success: true, data: { message, username? } }` | 401 UNAUTHORIZED, 403 FORBIDDEN, 422 VALIDATION_ERROR, 409 USERNAME_TAKEN 또는 USERNAME_ALREADY_SET, 500 INTERNAL_ERROR |

일반 API 실패 응답은 `{ success: false, error, code }`로 통일한다. 기존 필드와 메시지를 읽는 호출부도 함께 전환한다. 이미 열려 있는 화면의 구 요청은 수용하고, 구 응답을 기대하는 화면은 필요 시 새로고침 안내 등 전환 처리를 검증한다.

## 5. 완료 기준

- [ ] 아이디가 있는 한 계정에 이메일·아이디 어느 쪽으로 로그인해도 같은 user.id·권한·콘텐츠를 조회한다.
- [ ] 아이디 없는 기존 회원은 이전 이메일·비밀번호로 계속 로그인한다.
- [ ] 아이디의 대소문자·앞뒤 공백은 정책대로 처리하고, 이메일 기존 로그인 및 비밀번호의 원문 비교는 유지한다.
- [ ] 빈 값·길이 초과·허용되지 않은 문자·비문자열 입력은 클라이언트와 서버에서 안전하게 거부한다.
- [ ] 없는 계정·잘못된 비밀번호·차단 계정·비밀번호 없는 계정으로 로그인하면 세션이 생성되지 않는다.
- [ ] 아이디 없이 가입 / 아이디 포함 가입 / 가입 후 자동 로그인이 모두 정상 동작한다.
- [ ] 동일 아이디의 대소문자 변형·동시 가입 충돌에서 한 계정만 저장되며, 나머지는 정해진 중복 오류를 받는다.
- [ ] 기존 회원이 비밀번호 확인 후 아이디를 등록하면 즉시 두 방식으로 로그인한다.
- [ ] 인증 없는 등록·다른 계정 대상 등록·현재 비밀번호 오류·등록 후 재변경·동시 최초 등록을 거부한다.
- [ ] 프로필 이름 변경·비밀번호 변경·이메일 복구·소셜 로그인·관리자 권한·로그인 리다이렉트가 유지된다.
- [ ] user/me 응답을 사용하는 카드뉴스 편집 화면 등 기존 호출부가 정상 동작한다.
- [ ] 모바일·키보드·Enter 제출·자동완성·로딩·네트워크 오류·중복 제출 동작을 확인한다.
- [ ] 테스트 탐색·실행 포트를 검증하고 타입 검사·빌드를 통과한다. 기존 실패와 이번 변경으로 생긴 실패를 구분해 기록한다.
- [ ] 마이그레이션 전후 기존 회원·콘텐츠·결제 관계가 보존되고 이전 앱 버전으로 롤백해도 이메일 로그인이 동작한다.

## 6. 대안과 범위 제한

| 대안 | 판단 |
|---|---|
| username 별도 컬럼 + 통합 입력 | 권장. 명시적 아이디, 중복 제약, 기존 계정 유지 가능 |
| 이메일 앞부분을 아이디로 취급 | 제외. 서로 다른 도메인의 이메일 간 충돌과 의도하지 않은 별칭 발생 |
| name을 로그인 아이디로 사용 | 제외. 표시 이름은 중복 가능하고 로그인 식별자와 역할이 다름 |
| 이메일을 제거하고 아이디 전용 가입 | 제외. 요청은 로그인 방식 추가이며 기존 복구·소셜·계정 연결 흐름까지 바꿀 필요 없음 |

1차 제외: 아이디 변경·삭제, 아이디 찾기 메일, 이메일 없는 가입, 소셜 전용 계정의 비밀번호 신규 설정, 관리자 대리 아이디 변경, 별도 실시간 중복조회 API, 전체 인증 시스템 리팩토링.

이 계획 자체는 실행 승인을 의미하지 않는다. AGENTS.md 및 Prisma 스키마의 변경 제안·승인 규칙에 따라, 구현 착수 시 이 문서의 정책과 DB/API 변경 범위를 승인받은 뒤 진행한다.
